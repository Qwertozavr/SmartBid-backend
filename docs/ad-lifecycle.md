# Жизненный цикл объявлений

Документ описывает публикацию, 24-часовой таймер, ставки, удаление и
автоматическое завершение объявлений.

## Ответственность компонентов

- Backend хранит состояние объявления, запускает таймер и выполняет переходы
  между статусами.
- PostgreSQL обеспечивает атомарные обновления и блокировку объявлений при
  завершении.
- Outbox dispatcher публикует события в Kafka после фиксации транзакции.
- Telegram-бот получает события как Consumer и обновляет сообщения. Бот не
  управляет таймером и не определяет итоговый статус объявления.

## Статусы и переходы

```text
created   -> published | removed
published -> bought | expired | removed
removed, bought, expired -> конечные состояния
```

Назначение статусов:

| Статус | Описание |
| --- | --- |
| `created` | Объявление создано, но торги ещё не начались |
| `published` | Объявление опубликовано, ставки разрешены до `expires_at` |
| `bought` | Таймер завершён, победитель записан в `pretendent_id` |
| `expired` | Таймер завершён, победителя нет |
| `removed` | Объявление удалено владельцем чата |

Из конечного состояния перейти в другой статус нельзя.

## Таймер

Таймер запускается при переходе объявления из `created` в `published`.

Слой сервиса задаёт фиксированную длительность:

```text
published_at = текущее время
expires_at   = published_at + 24 часа
```

Новые ставки не продлевают таймер. Ставка в момент `expires_at` или позднее
отклоняется, даже если worker ещё не изменил статус объявления.

Фоновый worker запускается раз в минуту и выбирает просроченные объявления в
статусе `published`:

- при заполненном `pretendent_id` переводит объявление в `bought`;
- при пустом `pretendent_id` переводит объявление в `expired`.

Допустимая задержка фактического изменения статуса после `expires_at` составляет
до одной минуты.

## HTTP-сценарии

### Публикация

```http
POST /api/v1/ads/{id}/publish
Content-Type: application/json

{"chat_id":123}
```

Backend проверяет совпадение `chat_id`, разрешённость перехода из `created` и
устанавливает `published_at` и `expires_at`.

### Повышение цены

```http
POST /api/v1/ads/{id}/increase
Content-Type: application/json

{"pretendent_id":456}
```

Цена повышается на 5%. Ставка принимается только для активного объявления в
статусе `published`, когда `expires_at` ещё не наступил. Один пользователь не
может сделать две последовательные ставки.

### Удаление

```http
POST /api/v1/ads/{id}/remove
Content-Type: application/json

{"chat_id":123}
```

Удаление разрешено из `created` и `published`. Backend проверяет совпадение
`chat_id`, переводит объявление в `removed` и создаёт событие завершения.

### Получение объявления

```http
GET /api/v1/ads/{id}
```

Ответ содержит nullable-поля `published_at` и `expires_at`. До публикации оба
значения равны `null`.

Полные схемы запросов и ответов приведены в [OpenAPI](openapi.yaml).

## Событие завершения

Конечные статусы `removed`, `bought` и `expired` публикуются в Kafka:

- топик: `ad-finished` по умолчанию;
- тип события: `ad.finished`;
- настройка топика: `KAFKA_AD_FINISHED_TOPIC`.

Payload:

```json
{
  "event_id": "uuid",
  "ad_id": "uuid",
  "status": "removed|bought|expired",
  "pretendent_id": 456,
  "final_price": 105
}
```

Если победителя нет, `pretendent_id` имеет значение `null`.

Telegram-бот должен использовать `event_id` для идемпотентной обработки:
повторно полученное событие не должно повторно изменять сообщение или выполнять
другие побочные действия.

## Надёжность и конкурентность

- Изменение конечного статуса и запись `ad.finished` в outbox выполняются в
  одной транзакции.
- Worker выбирает объявления через `FOR UPDATE SKIP LOCKED`, поэтому несколько
  экземпляров backend не завершают одно объявление одновременно.
- Ставка обновляет цену условно: объявление должно оставаться `published`, а
  `expires_at` должен быть позже текущего времени.
- Удаление читает объявление под блокировкой, поэтому событие содержит последнюю
  зафиксированную цену и претендента.
- Уникальность outbox по объявлению и типу события предотвращает создание
  нескольких событий `ad.finished`.
- Ошибки публикации повторяются, после исчерпания попыток сообщение отправляется
  в Dead Letter Queue.

## Ошибки

| Ситуация | HTTP-код |
| --- | --- |
| Некорректное тело, `chat_id` или переход статуса | `400` |
| Ставка после завершения таймера | `400` |
| Объявление не найдено | `404` |
| Ошибка хранилища или транзакции | `500` |

Внутренние ошибки PostgreSQL и Kafka не возвращаются клиенту напрямую.

## Ограничения безопасности

Проверка совпадения `chat_id` при публикации и удалении подтверждает
согласованность запроса с объявлением, но не аутентифицирует вызывающего
клиента. До добавления полноценной аутентификации доступ к API должен быть
ограничен доверенным Telegram-ботом или внутренним сетевым контуром.

Backend отклоняет неизвестные JSON-поля, ограничивает размер тела запроса и не
возвращает клиенту внутренние ошибки хранилища. Дополнительные требования и
план развития приведены в [заметках по безопасной разработке](security.md).
